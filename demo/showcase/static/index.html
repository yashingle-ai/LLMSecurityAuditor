The auditor reads an LLM app's prompts, code, tool definitions, configuration, documents and conversation logs, and reports what an attacker could exploit, with the evidence and the fix. Where does it come from?

Every check the auditor runs

Each check has an ID: the letter says what part of the app it looks at. Each one maps to the OWASP Top 10 for LLM Applications (LLM01–LLM10) and the OWASP Top 10 for Agentic Applications (ASI01–ASI10).

How the auditor works

One command, one scope file. Nothing is sent to a model or to the app under test: the auditor reads files and logs, and everything runs on this machine.

  1. Scope fileSays what to audit (prompts, code, tools, configs, logs, documents) and what the app can do: who can reach it and what its tools can touch.
  2. IngestionLoads every input into one model: prompts, tool definitions, conversations with their tool calls, documents with their hidden text.
  3. 48 checksPattern rules, Semgrep taint rules, an injection classifier, and data-flow tracking across tool calls.
  4. Scoring and linkingSeverity follows a fixed rubric. Evidence from the logs confirms static findings, and linked findings point to each other.
  5. ReportsJSON for machines, Markdown for people, SARIF for GitHub code scanning. Secrets and personal data are redacted everywhere.

Four kinds of finding

Vulnerability
Exploitable, with proof. Example: the logs show the model repeating a key from its system prompt.
Weakness
A design or configuration flaw that hasn't been exploited yet. Example: a key pasted into the system prompt.
Hardening
Best-practice advice. It has no severity and never fails a build.
Incident
An attack someone tried, seen in the logs, marked succeeded, failed or unknown. An attack that succeeded turns the weakness it got through into a vulnerability.

How severity is scored

score = base impact + context + capabilities

  • Base impact (0–10): set by each check. A key in the system prompt is 7; model output reaching a shell is 9.
  • Context: +1 each for internet-facing, autonomous, sensitive data, and multi-tenant; −1 for low-sensitivity data.
  • Capabilities: +1 for each tool capability that makes the issue worse, such as sending email or running code, up to +2.

0 info · 1–3 low · 4–6 medium · 7–8 high · 9–10 critical. Confidence is reported separately and never lowers severity, so an unconfirmed critical issue still reads as critical.

Where an LLM app can be attacked

Every check names the trust boundary it guards.

BoundaryWhat crosses itTypical attacks
B1 User → AppUser messages, uploadsDirect prompt injection, jailbreaks
B2 App → LLMSystem prompt, templatesSecrets in prompts, unsafe templates
B3 Content → ContextWeb pages, emails, documents, tool resultsIndirect injection, hidden instructions
B4 LLM → ToolsTool calls and argumentsExcessive agency, exfiltration chains
B5 Output → SinksText rendered, run, or storedXSS, code execution, data-leaking links
B6 Agent ↔ MemoryMemories written and recalledPoisoned memories
B7 Agent ↔ MCP serversTool definitionsTool poisoning, changed definitions, look-alike names
B8 App ↔ ProviderKeys, limits, logs, dependenciesLeaked keys, no cost limits, personal data in logs

How sure is a finding?

Deterministic
A recorded fact: a canary token in a reply, a logged tool call, a value traced from one tool into another.
Rule
A pattern or Semgrep rule matched.
Classifier
The injection classifier scored the text above its threshold.
Attestation
An answer in the scope file, for facts the code can't show (such as the provider's data retention).
